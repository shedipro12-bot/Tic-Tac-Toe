# תוכנית אבן דרך 5 — גרסה מאוחסנת אמינה

סטטוס: המימוש המקומי התחיל בעקבות בקשת המפתח לבנות את אבן הדרך. התוכנית המקורית נשמרת להלן; מצב הבדיקות והפערים העדכני מתועד ב־[מסירת אבן דרך 5](MILESTONE-5-REVIEW.md). המפתח בחר בפרויקט Cloudflare Pages חדש; חיבור החשבון ו־GitHub זמין, והפרסום בתהליך.

## מטרה ונקודת מוצא

להעמיד מועמד לשחרור של ה־MVP ב־Cloudflare Pages: HTTPS, עדכונים לפי בחירת המשתמש, הגנה על משחק חי, כותרות אבטחה ומטמון נכונות, ובדיקות במכשירים אמיתיים ובמשתמשי ניסיון.

מקורות: [Codex.md](../Codex.md), [אבן דרך 5 ותנאי הסיום](MILESTONES,md.md), [PRD](PRD.md.md), [ARCHITECTURE](ARCHITECTURE.md.md), [DESIGN](DESIGN.md.md), [Wireframes](wireframes.png.png), [Mockups](mockups.png.png), [Style guide](style-guide.png.png) ו־[מסירת אבן דרך 4](MILESTONE-4-REVIEW.md).

נקודת המוצא היא `b127e06`, שהועלה לענף main בריפו [Tic-Tac-Toe](https://github.com/shedipro12-bot/Tic-Tac-Toe). קיימים המשחק המלא, מונים זמניים, הגדרות, משוב, manifest, אייקונים ומטמון מלא. במסירה האחרונה עברו 59 בדיקות יחידה, 69 בדיקות דפדפן ו־12/12 מקרי קבלת offline, ואומתה התקנה אמיתית ב־Chrome במחשב. עדיין חסרים hosting, כותרות HTTP, ממשק עדכון, בדיקות החלפת גרסאות בין טאבים, מכשירי Android/iOS ובדיקת שימושיות.

בקשת התכנון מאפשרת להכין את המסמך. הוראה לבנות את אבן הדרך תאפשר להתחיל במימוש; הגישה לחשבון וסביבת הפרסום ייקבעו במסגרת העבודה המאושרת. אישור סופי של ה־MVP נשאר בידי המפתח.

## התוצאה למשתמש

- כתובת HTTPS של משחק סטטי, הפועל בדפדפן ובאפליקציה מותקנת לאחר שמירה מלאה.
- גרסה חדשה ממתינה בזמן משחק. כפתור **Update and reset session** מוצע ב־Setup, לאחר תוצאה או בהתאוששות; המשתמש יכול להמשיך להשתמש בגרסה הנוכחית.
- בחירת העדכון מפעילה את הגרסה המוכנה ופותחת הפעלה חדשה: Setup, Medium, מונים אפס ושני מתגי המשוב On.
- עדכון שהופעל בטאב אחר אינו מרענן טאב פעיל. הלוח, תור המחשב, המונים וההעדפות שלו ממשיכים כרגיל; לאחר סיום מוצעת החלפה לפי בחירה מקומית.
- משחק ממשיך כשהכנת עדכון נכשלת. הודעת מוכנות offline נשענת על מלאי הגרסה המתאימה, ולא על נוכחות עדכון או רשת בלבד.
- אין שינוי בחוקים, הסתברויות היריב, זמני התורות או חוזי האיפוס. אין מסך התקנה מותאם, אישור ל־Restart, הדרכה, חשבון, analytics או שרת משחק.

## סדר העבודה

### 1. הכנת בנייה וסביבות פרסום

- לתעד את חשבון Cloudflare והפרויקט שהמפתח בחר, ולחבר את הריפו הקיים באמצעות Git integration בהרשאה המצומצמת הנדרשת. כתובת pages.dev מספיקה; domain מותאם הוא אפשרות עתידית, ולא תלות של אבן הדרך.
- הצעת ענפים: main ל־production, ו־codex/milestone-5 לפיתוח ולתצוגה מקדימה. זו הצעה; אין ליצור ענף, לבצע merge או לחבר פרסום במסגרת התכנון.
- להגדיר root של הפרויקט כשורש הריפו, פלט dist, ופקודת בנייה מוצעת `npm ci && npm test && npm run build`. הפקודות כבר קיימות; `npm run build` כולל טיפוסים ובדיקת precache.
- להצמיד Node ‏24.15.0 שנבדק בפרויקט באמצעות `.node-version` או `NODE_VERSION`, ולהגדיר `SKIP_DEPENDENCY_INSTALL=1` כדי שהתקנת התלויות תיעשה ב־npm ci. לבדוק בפלט Cloudflare את גרסת Node/npm בפועל ואת הצלחת קובץ הנעילה; אין להסתמך על engines בלבד. מנגנוני הבחירה מתועדים ב־[Cloudflare build image](https://developers.cloudflare.com/pages/configuration/build-image/).
- להשתמש באותן הגדרות בנייה ב־preview וב־production. לתעד commit, מזהה build מתוך המלאי, deployment ID וכתובת לכל מועמד; UUID הבנייה הקיים מייצר נכסים שונים בין בניות, ולכן commit לבדו אינו מוכיח זהות של פלט.
- להפעיל preview ב־origin נפרד ולוודא ש־worker/cache אינם ניגשים ל־production. לבדיקת A→B להשתמש ב־alias קבוע של ענף preview: שתי כתובות deployment בעלות hashes שונים הן origins שונים ואינן מוכיחות עדכון באותו origin. כתובת deployment קבועה תשמש לתיעוד המועמד. [Cloudflare preview deployments](https://developers.cloudflare.com/pages/configuration/preview-deployments/).
- להכין מועמד, בדיקות וראיות לפני מעבר לסביבת production במסגרת הוראת הפרסום המתאימה. חיבור Git integration עלול לפרסם אוטומטית pushes לענף production, ולכן את בקרת הענפים יש להגדיר כחלק מהחיבור עצמו.

תוצר: בנייה שחזורית מתלויות נעולות ותצוגה מקדימה מבודדת, עם כתובת וגרסה מתועדות. לא מוסיפים Functions, backend, Cloudflare Web Analytics או שירות משחק.

### 2. כותרות אבטחה, HTTP ונתיבים חסרים

- להוסיף `public/_headers`, ולהבטיח העתקה ל־dist. להחיל את ה־CSP המדויק מהארכיטקטורה:

```text
default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; media-src 'self'; font-src 'self'; connect-src 'self'; worker-src 'self'; manifest-src 'self'; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; form-action 'none'
```

- להוסיף `X-Content-Type-Options: nosniff`, ‏`Referrer-Policy: no-referrer` ו־`Permissions-Policy: camera=(), microphone=(), geolocation=()`.
- להגדיר revalidation למסמך השורש, index.html, sw.js, manifest.webmanifest, boot-meta.json, קובצי העזר sw-support ולמלאי האבחון. אייקונים, טקסטורות וצלילים יכולים להישאר ב־revalidation גם עם שם בעל גרסה.
- להגדיר `Cache-Control: public, max-age=31536000, immutable` רק לנכסי build בעלי hash. לבדוק שאין קובץ בלתי מגורס שנכלל בכלל /assets/. להימנע מחפיפת כללי Cache-Control היוצרת ערכים סותרים; Pages מצרף ערכי header החלים יותר מפעם אחת. [Cloudflare static headers](https://developers.cloudflare.com/pages/configuration/headers/).
- לבטל את fallback ה־SPA הרחב של המארח באמצעות 404.html סטטי בשורש. האפליקציה דורשת נתיב אחד בלבד. הבדיקה תדרוש 404 אמיתי לנכס חסר ול־/api/*, בלי תוכן index.html של המשחק ובלי להציג HTML כ־JS או MP3. דף 404 של המארח יכול להיות HTML עם status 404; הוא אינו מסך חדש במשחק. ברירת המחדל של Pages תלויה בקיום קובץ זה. [Serving Pages](https://developers.cloudflare.com/pages/configuration/serving-pages/).
- לבדוק GET אמיתי מקוון כשה־worker מנוטרל או בהקשר נקי: root, index.html וההפניות שלו, manifest, worker, עזריו, גופן, CSS, JS, SVG, אייקון ו־MP3. לתעד status, Content-Type, Cache-Control וכל כותרות האבטחה. לבדוק גם revalidation עם ETag כאשר נתמך ותגובות לנכסים חסרים.
- לבדוק את CSP בדפדפן בגרסה המאוחסנת, כולל אודיו, CSS, SVG, manifest, רישום worker והודעות בין הדף ל־worker. לתקן שימוש אסור במקום להוסיף unsafe-inline/unsafe-eval או origins מרוחקים. בבדיקת מקור התגובות להפריד HTTP של המארח מתגובות שכבר שמורות ב־worker.

תוצר: מדיניות המיושמת בפועל בתגובות HTTPS, עם משחק תקין תחת CSP. היעדר שגיאות ב־Vite preview לבדו אינו הוכחה לכותרות Cloudflare.

### 3. עדכון ממתין ובחירת משתמש

- להרחיב את `src/pwa/register.ts` במצב עדכון נפרד מ־GameState: worker ממתין, גרסה שכבר הופעלה מבחוץ, החלפה שנבחרה בטאב זה וכשל החלפה. לשמר רישום יחיד, prompt ו־skipWaiting כבוי בעדכון רגיל.
- לחבר onNeedRefresh ולשמור אפשרות להפעיל worker ממתין. להשאיר onNeedReload בבעלות האפליקציה: בתוסף 2.0.0 המותקן, controlling יכול להוביל לרענון ברירת מחדל, והעברת false לפונקציית updateSW אינה ערובה למניעתו. לאמת מול הקוד המותקן ובבדיקת שני builds; דוגמת [Vite PWA prompt](https://vite-pwa-org.netlify.app/guide/prompt-for-update.html) אינה מספיקה לחוזה בין טאבים.
- לקבל הודעת גרסה ולוודא מלאי מלא מה־worker המיועד לפני החלפה. לא להציע התקנה כושלת או worker redundant כעדכון מוכן. מוכנות גרסה B אינה הוכחה למוכנות של המסמך הישן A.
- להוסיף `UpdateNotice` נגיש באזור status על משטח הקרם, בלי modal ובלי לשנות את הלוח. הכפתור המדויק הוא **Update and reset session**, עם focus ברור ויעד מגע לפחות 44×44. בהסתרת הכפתור בזמן משחק ממתין אין צורך בכפתור ביטול נוסף.
- מצב בטוח נבחן לפי phase: setup/finished/error, וב־render recovery שבו המשחק אינו שמיש. Settings אינו מצב בטוח בפני עצמו: אם נפתח ממשחק פעיל, העדכון נשאר מוסתר גם כשהמחשב מסיים תור. כשהמשחק מסתיים, ניתן להציע את הפעולה בלי לשבש את Back.
- לבדוק שוב את המצב בעת לחיצה, ולמנוע לחיצה כפולה או תחילת משחק חדש באמצע ההחלפה. להפעיל רק את ה־worker המוכן, להמתין לשליטה של הגרסה הצפויה ולהטעין מסמך חדש פעם אחת בעקבות בחירת הטאב הזה.
- אם B הופעלה בטאב אחר, לשמור כאן את מצב המשחק ולעדכן שהמסמך נשאר בגרסה A. הפעולה במצב בטוח יכולה לרענן ישירות לגרסה הפעילה B לאחר אימות המשאבים, גם כשאין עוד worker ממתין.
- לטפל בכשל activation, worker שלא השיב, רשת שנפלה או update שטרם הושלם באמצעות המתנה מוגבלת ומסר לא חוסם; לשחרר את בקרות הממשק ולהשאיר את הגרסה השמישה. להסיר מאזינים וטיימרים של ניסיון שהסתיים.
- לשמר את Connection needed וההתאוששות של bootstrap. אם נדרשת פעולה גם במעטפת זו, להשתמש ברישום הקיים בלי להוסיף רישום שני; רענון לשם תיקון אותה גרסה נשאר נפרד מהסכמה להחלפת גרסה.

תוצר: המשתמש בוחר מתי לאפס הפעלה לצורך עדכון, ואירועי worker אינם dispatch של RESET_SESSION או של מהלכי משחק.

### 4. בדיקות אמיתיות של החלפת builds

להוסיף סביבת בדיקה המגישה שתי בניות production ‏A ו־B באותו origin וב־scope /, שומרת את A לפני הכנת B ומחליפה את הגרסה המוגשת בלי למחוק profiles, registrations או caches. להוכיח שה־build IDs שונים, שהתקנת B הושלמה ושהוא waiting; אירוע מלאכותי לבדו אינו ראיה לעדכון.

מקרי החובה:

1. B ממתין ב־Setup: ההצעה מופיעה; ללא בחירה המסמך A נשאר; בלחיצה מתקבלת B ו־defaults מלאים.
2. הגעה בזמן תור אדם ובזמן תור מחשב: אין רענון, תור אבוד או ספירה כפולה; ההצעה מופיעה רק בסיום/התאוששות.
3. Settings בזמן משחק ובתוצאה: הלוח, המונים וההעדפות נשמרים; phase קובע בטיחות.
4. טאב בטוח מפעיל B וטאב אחר משחק A: הטאב הפעיל אינו מתרענן, ממשיך משחק ומסיים אותו; לאחר בחירה שלו נטענת B ומאופסת רק הפעלתו. לבדוק זהות מסמך ומספר רענונים, לא רק טקסט על המסך.
5. אותו תרחיש עם טאב מוסתר/חזרה לנראות ועם חלון מותקן כשניתן: אין רענון אוטומטי בחזרה לרקע/קדמה.
6. שתי לחיצות update או הפעלה מקבילה בשני טאבים: החלפה אחת לכל מסמך שנתן הסכמה, ללא לולאת רענון או מהלך ישן.
7. כשל אמיתי בהורדת משאב של B לפני activation: A נשאר שמיש ואף נפתח offline; אין הצעת עדכון מוכנות מטעה. לתעד שהבקשה הכושלת שייכת ל־worker.
8. עדכון שמור ומוכן ללא רשת: החלפה מצליחה אם כל B קיים; כשל אימות/הפעלה אינו גורם לרענון למסך ריק.
9. לאחר B: פתיחה offline, כל הקשיים, תוצאות, מונים, Replay/Restart ומשוב. Cache Storage אינו מכיל gameplay או preferences ומטמון זר אינו נמחק.
10. rollback ב־preview לגרסה קודמת מתקבל כעדכון ממתין נוסף, ושומר על אותם חוזי בחירה ואיפוס.

לצד הבדיקות המקומיות, להדגים A→B ב־alias HTTPS הקבוע של preview ולאמת שהמארח מחזיר את B. אין לערבב כתובות hash שונות או להסתמך על HTTP cache כהוכחת precache.

### 5. מכשירים, offline ושימושיות

**מטריצת תאימות מתוכננת:** Android Chrome יציב נוכחי וקודם; iOS Safari יציב נוכחי וקודם. בכל גרסה: דפדפן ומצב מותקן — **8 סביבות יעד**. בכל סביבה portrait/landscape, מגע, safe-area, מקלדת לפי זמינות, גלילה וניגודיות, חזרה מהרקע, reset, משוב, offline ועדכון. לתעד device/OS/browser המדויקים בעת הקפאת המועמד; המסמך אינו מניח מה יהיו מספרי הגרסאות ביום השחרור.

נדרש מכשיר פיזי או שירות בדיקה המשתמש במכשירים אמיתיים. אמולציית viewport, WebKit ו־Chrome במחשב מסייעות לבדיקות אך אינן מחליפות התקנה ב־iOS או בדיקת Android. גרסה קודמת שאינה זמינה נשארת פער לא מושלם; אין לשנות בשקט את מדיניות התמיכה או להוציא אותה מהמכנה.

לפני הקפאת המועמד יש להשוות את Vite build.target ואת תכונות JS/CSS שבשימוש לגרסה הוותיקה ביותר במטריצה. אם הפלט אינו תואם, להתאים אותו ולבדוק שוב; אין לצמצם תמיכה בשקט או להוריד קוד תאימות מרוחק בזמן משחק.

**מכנה offline מתוכנן:** 8 תרחישים בכל אחת מ־8 הסביבות, סך **64 מקרי קבלה**:

1. טעינה מקוונת מלאה, סגירה ופתיחה חדשה ללא רשת, והפעלה חדשה ב־defaults.
2. השלמת משחק offline ב־Easy.
3. השלמת משחק offline ב־Medium.
4. השלמת משחק offline ב־Hard.
5. ניצחון/הפסד/תיקו, מונים, קושי הבא ו־Play Again.
6. Restart בתור מחשב וביטול מהלך ישן.
7. Settings, ארבעת שילובי המתגים, אודיו ממשי ותנועה מופחתת לפי תמיכת מערכת.
8. ניתוק/רקע שומרים מסמך חי; רענון/פתיחה חדשה מאפסים; portrait/landscape נשארים שמישים.

להכין דף צעדים וראיות לכל תרחיש לפני הריצה, ולהריץ על המועמד המדויק לאחר שמירה מלאה. המדד הוא עברו/64, יעד **100%**; כשל או בדיקה שלא בוצעה נשארים במכנה. סביבה שתסווג כלא תומכת בהתקנה תחייב דיווח פער והחלטה מפורשת על מדיניות, לצד בדיקה בדפדפן. 12 מקרי desktop מ־M4 נשארים בדיקות נסיגה נוספות ואינם תחליף למטריצה.

**שימושיות לפני שחרור:** הצעת מדגם מינימלי של **10 משתתפים**, לחלוקה מוצעת 3 בגילי 5–7, 4 בגילי 8–12 ו־3 בגילי 13–17+. לתאם עם המפתח ולתעד את המדגם והמכשירים לפני הבדיקה; שינוי במדגם יתועד מראש, ולא כדי לשנות תוצאה שכבר נמדדה.

- משימה ניטרלית אחת: לבחור רמת קושי רצויה ולהתחיל משחק, בלי להסביר כפתורים או להדגים מראש. הצלחה דורשת בחירת קושי ותחילת משחק בפועל בניסיון הראשון וללא עזרה.
- רישום ידני אנונימי של קוד משתתף, קבוצת גיל, סביבת בדיקה והצלחה/כשל. ללא איסוף שמות, חשבונות או פרטים דרך האפליקציה.
- יעד **לפחות 9/10 = 90%**. עזרה שניתנה נחשבת כשל במשימה; לא מוציאים משתתף מהמכנה בגלל קושי. קושי שנמצא מתועד לצורך תיקון UX בתוך האפיון ובדיקה חוזרת במדגם חדש ומתועד, עם שמירת התוצאה המקורית.
- התרשמות מהשלמת משחק וחזרתיות נמדדת בנפרד לאחר משימת ההתחלה, כדי לא להדריך את המשתתף לפני מדידת ה־KPI.

תוצר: ראיות לתאימות ויעדי PRD. אין להוסיף telemetry לייצור לצורך המדידה.

### 6. אימות גרסת השחרור ומסירה

- לשמר את בדיקות M1–M4 ולהוסיף בדיקות עדכון, HTTP ו־CSP. להריץ npm ci בסביבה נקייה, npm test, npm run build ו־npm run test:e2e מול production. להתאים בדיקות לשימוש בכתובת hosted בלי לשנות scope/manifest לצורך הבדיקה.
- בדיקת ההתקנה הקיימת דורשת Chrome עם desktop session. לתעד זאת בנפרד ממערכת הבנייה של Pages; אין להציג דילוג בסביבת CI ללא desktop כהצלחת התקנה. להגדיר פקודות בדיקה חדשות רק בזמן המימוש ולתעד אותן ב־package.json וב־README.
- לבדוק network/storage במצב נקי, במשחק, ב־Settings ובעדכון: בקשות נכסים מקומיות בלבד, בלי analytics, API משחק, remote AI, events או נתוני משחק. להפריד עיבוד בקשות ולוגים תפעוליים של Cloudflare מהיעדר telemetry באפליקציה.
- לבצע בדיקת HTTPS קצרה גם ב־production לאחר הפרסום: מסמך, headers, assets, רישום worker, משחק ואימות offline. לייחס את הראיות לגרסה ול־origin הנכונים; build אחר של אותו commit מחייב אימות המלאי שלו.
- לשמור צילומים, דוחות וראיות תחת `artifacts/milestone-5/`, כולל UI עדכון, שני טאבים, כשל עדכון, תגובות HTTP, offline במכשירים ותוצאות שימושיות אנונימיות. שומרים את הראיות מאבני הדרך הקודמות.
- לעדכן README, להוסיף `spec/MILESTONE-5-REVIEW.md` ומסמך פרסום/rollback לפי הצורך. לפרט כתובת מועמד וייצור, commit/build/deployment, גרסאות, עברו/64, עברו/10, בדיקות אוטומטיות וכל פער אמיתי.
- למסור לבדיקה ולעצור. פער חשבון/מכשיר/משתתפים אינו מונע הכנת יתר המימוש, אך תנאי תלוי שלא נבדק נשאר לא הושלם. ה־MVP נחשב מאושר רק לאחר אישור מפורש מהמפתח.
